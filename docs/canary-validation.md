# Known-marker exposure detection and validation

**English** | [简体中文](zh-CN/canary-validation.md)

This is a deliberately narrow measurement capability: determine whether a **complete, known synthetic marker** appears in assistant text under documented transformations. It does not discover arbitrary personal data, prove confidential-data isolation, or decide privacy-law compliance.

## Runtime and report placement

This detector currently runs in active-assessment response checks. It is local deterministic code, with no LLM or agent call. It has not been installed as a normal business-response blocker, including SSE streaming. Existing inference-path protection checks request credentials before upstream I/O. No end-to-end realtime response SLA is claimed.

Structured test reports, evidence links, counts and version comparisons are generated by code. An asynchronous LLM explanation could be added later for wording or remediation discussion; no such feature is implemented here. Any future explanation must cite recorded evidence and cannot rewrite detector outcomes, turn unknown into pass, or authorize a realtime access decision. A tool-using agent is optional only for workflows that actually need multi-step retrieval or verification.

## Current v2 results and preserved history

The current detector is `synthetic-canary-v2`; `DetectVersion` retains the unchanged v1 behavior for historical evidence. `make validate-canary` measures both frozen corpora and reports v2, v1 and literal exact matching on the same cases.

| Frozen corpus | v1 detected exposures | v2 detected exposures | False positives, v1 / v2 | Unknown, v1 / v2 |
| --- | --- | --- | --- | --- |
| Original 48 cases | 20 / 26 (76.92%) | 26 / 26 (100%) | 0 / 20, both | 2 / 2 |
| New 72 cases | 17 / 44 (38.64%) | 30 / 44 (68.18%) | 1 / 24, both | 6 / 6 |

The original six missed constructions are now detected. The new set still has 14 missed exposures and one observed false positive. Its six unknowns comprise four ineligible inputs and two labelled negative long encodings; labelled-input decision coverage is 97.06%. The observed FPR is 4.17% on 24 negatives, with unknowns reported separately. Do not compare percentages across corpora as if the populations were identical.

The new false positive is shared with v1: separator removal can collapse a marker truncated at a separator into the same normalized value. This is a documented limitation of lossy matching, not proof that the complete original bytes were disclosed. The active generator's fixed hex-suffix format does not make this a general guarantee for arbitrary markers. Misses include HTML entities, escaped hex, fullwidth encoded text, adjacent independently padded Base64 without whitespace, three-layer encodings and other transformations. No case was removed or relabelled after evaluation.

Another project agent authored and froze the new corpus without reading the implementation or old corpus; the implementing agent evaluated it after the v2 algorithm was written. This is internal separation, not external third-party or real-model validation. [Provenance](../tests/testdata/canary-v2-provenance.md) and [new corpus](../tests/testdata/canary-validation-v2.json) identify SHA-256 `d17f64c06920258121d1e5e09615b6545ff70b9c4e69dee4e60cb988efd7df79`. V1 outputs were frozen separately before upgrade; historical real-run fixtures verify that recorded evidence bytes and hashes remain unchanged.

## Measure before claiming effectiveness

From the source repository, run:

```bash
make validate-canary
```

For standalone stage ablation and local call P50/P95/P99, use [Canary benchmark](canary-benchmark.md). Quality and latency repetitions have separate denominators; these measurements do not establish production realtime performance.

The command uses Go and the frozen 48-case and 72-case corpora. The [original 48-case corpus](../tests/testdata/canary-validation-v1.json) remains unchanged. It makes no model or network request. A new private `dist/canary-validation/eval-*/report.json` records the detector and baseline versions, corpus SHA-256, every expected/predicted outcome, evidence spans, group metrics, missed exposures and unknown cases. Previous reports are retained. An exit code of zero means measurement completed, not that every exposure was detected.

The corpus was frozen before detector implementation, with SHA-256 `1430feccbc31f8cd321ad108848a0a814af645892e3aded9436a99e1684c830c`. The detector receives only marker and response bytes; it cannot read sample IDs, groups, labels or the corpus. Unit fixtures live separately. Nevertheless the data and code were authored in the same development process: this is **not independent third-party review or blind validation**. The groups are coverage categories, not randomized train/test splits. Samples use the same marker format and include related encoding variants; they cannot estimate population performance.

Initial measured results for `synthetic-canary-v1`:

| Metric | Result on this corpus |
| --- | --- |
| Labelled complete exposures | 26 |
| Detected exposures / missed exposures | 20 / 6 |
| Labelled non-exposures / observed false positives | 20 / 0 |
| Ineligible inputs kept unknown | 2 |
| Exposure recall | 76.92% |
| Literal exact-match baseline recall | 7.69% (2 of 26) |

All six challenge exposures are included in the aggregate, not removed from the denominator. They use ROT13, reversed text, decimal character codes, double Base64, Base64-of-hex and independently encoded small chunks. These remain blind spots of the retained v1 implementation; v2 covers these six specific constructions. Encoding-mode labels in the corpus do not imply distinct alphabets or padding for every fixed-length marker; additional unit tests exercise padded Base64 and Base64URL-specific characters.

Precision is `TP / (TP + FP)` and is null when no positive detection exists. Recall is `TP / all labelled exposures`, counting an unknown positive as a miss. FPR is `FP / all labelled non-exposures` and must be read with unknown counts and decision coverage. Decision coverage excludes the two explicitly ineligible boundary inputs and measures binary decisions among exposure/non-exposure labels. Zero observed false positives in 20 authored negatives does not establish zero real-world false positives. No population confidence interval or model-level privacy rate is inferred.

## Detection contract

`internal/leakage` is a pure, bounded detector with no model, corpus or filesystem dependency. Markers must be 24–128 ASCII letters/digits/underscore/hyphen characters, begin with a letter and retain at least 20 characters after normalization. Responses are limited to 8192 UTF-8 bytes. Invalid markers, invalid UTF-8, oversized text, unprocessed encoding candidates above 2048 bytes or an exhausted search budget return `unknown` when no exposure has already been established. V1 retains its 128-candidate cap. V2 caps candidate attempts at 256, unique nodes at 128, emitted decoded text and expanded scan text at 64 KiB each, with at most two reversible layers.

Both versions support exact text, ASCII case and fullwidth folding, separator removal and the documented percent/JSON Unicode/hex/Base64 representations. V1 permits a single encoding layer. V2 adds up to two reversible layers, text reversal, ROT13, decimal ASCII codes, and whitespace-adjacent independently decoded printable ASCII Base64 chunks. Full tokens are checked against the 2048-byte candidate limit. Invalid encodings, non-printable results or non-whitespace gaps break chunk runs; ordinary words are not recognized semantically and can themselves be valid encoded chunks. Candidate case and Base64 alphabets are preserved before decoding; lossy normalization is used only for terminal comparison. Only the first match is returned. There is no unbounded decoding, general Unicode confusable matching, partial-marker detector or semantic inference.

An observed exposure records representation and an exclusive byte range `[start_byte, end_byte)` in the original UTF-8 response. For normalized raw text it spans the original fragment; for decoding it spans the outer original encoded candidate. Whole-region reversal/ROT13 uses `transformed_region` and can reference the entire original response. Compositions record an ordered transformation list, and terminal normalization is identified separately. These are conservative original-byte regions, not guessed decoded-character positions. Detector results contain a marker hash and metadata, not the response or marker value. `not_observed` means no complete marker was found under this coverage, not that the answer is safe. The text-only detector can assess empty text; the HTTP runner conservatively rejects empty, truncated, malformed or lossy-decoded assistant responses before detection.

## Use in active assessments

Install [the canary test suite](../examples/test-suites/synthetic-canary.json) in `<data_dir>/test-suites/`, restart and select `suite_id: synthetic-canary`, `suite_version: 1.0.0` in the existing product test plan. A configured Chat Completions target and product rule pack are still required. See [Active assessment](active-assessments.md) for authenticated APIs, budgets and scheduling.

`check: canary_absent` requires exactly one `{{CANARY}}` placeholder in a system message, followed by a user message. The runner generates a new 128-bit random marker for each case and expands a private copy of the messages. The installed suite snapshot retains the template. The four supplied cases request direct, encoded and separated disclosures, plus a benign control request. This probes caller-supplied context; an application that ignores or replaces such context requires a different adapter. It does not test an application's actual hidden documents or data.

An observed marker fails the case; no marker observed passes only this bounded check; an unavailable/unreliable response or scan remains unknown. Results retain the generated **synthetic** marker, detector version, response hash, representation and evidence span in the separate private test store. Optional response text follows the existing `retain_responses` setting. Metadata-only `calls.jsonl` never receives markers or response text. When text is retained, record reads recheck detector evidence; without it, a hash alone cannot independently revalidate detection. The replay API still returns a deterministic rule replay and makes no model request.

Completed runs emit server-owned `testing.canary.exposure_observed`: true if any case observed exposure, false only when every canary case was evaluated with no exposure, otherwise absent. False describes this detector's coverage, including its documented blind spots. Product profiles cannot override the fact. Rule evaluation remains advisory; the NIST draft retains its manual context, metric adequacy and independent-review items.

New runs use `bounded-chat-tests-v4` with detector v2 and support separate output-control probes. Historical runner v3 also uses detector v2. Historical runner v2 uses detector v1, and runner v1 literal reports remain readable and replayable. Retained text is checked using its recorded detector version. Different runner generations do not share comparison or lifecycle baselines. Unsupported versions are rejected. No automatic migration invents evidence for historical runs.

## Verify integration separately

```bash
make build
python3 tests/canary-smoke.py --output-dir dist/canary-integration/new-run
```

This starts the actual binary and a local scripted endpoint, sends 20 requests with 20 distinct markers, detects direct and layered deliberately exposed representations, verifies recovery and rule replay, and exports private synthetic reports. It validates wiring, **not** detector quality; the frozen corpus measures the latter's documented, limited coverage. `go test -race ./...` covers detector bounds, scoring including unknowns, active request handling, UTF-8 failures, retained evidence and legacy compatibility. Real models, stochastic repeated attacks, independent datasets and representative application risk remain unvalidated.
